1. 今の仕組みをざっくり理解する

あなたの今の構成はこんな感じです：

ブラウザ
(アプリ)
→
Cloudflare
Worker
→
Cloudflare
Tunnel
→
あなたの PC
LM Studio

Worker が 「受付係」の役割をしています。ブラウザから来たリクエストをチェックして、問題なければあなたのPCにある AI（Gemma）に転送します。

コンビニのバックヤードに高性能な製造機（Gemma）がある。直接お客さんを通したらまずいので、店員（Worker）がカウンターで対応して、必要なものだけを製造機に渡してくれる。

この「受付係 Worker」には今こんな機能があります：

APIキー（パスワード）をチェックして、知らない人は弾く
CORS対応（ブラウザからのリクエストを許可）
Cloudflare Tunnel への認証を自動で付与

2. なぜ「整備」が必要なのか

現状の問題点

今は 1つのパスワード（GEMMA_API_KEY） だけで全管理しています。

たとえばアプリが3つになった場合：

アプリ使っているキー
TaskJournal同じ
1つのキー
新しいアプリB
新しいアプリC
アプリCのコードが万が一流出 → 全アプリへのアクセスができてしまう

→ アプリごとに別のキーを使えば、1つ漏れても他は安全です。

家の鍵が全員同じだと、1人がなくしたら全員の鍵を交換しなければならない。部屋ごとに別の鍵なら、1つなくしてもその部屋の鍵だけ交換すればいい。

① 複数APIキー対応 最優先

やること

Cloudflare Worker の環境変数を GEMMA_API_KEY（1本）から GEMMA_API_KEYS（複数、カンマ区切り）に変更します。

変更前（今）：

GEMMA_API_KEY = abc123xyz

変更後：

GEMMA_API_KEYS = abc123xyz,def456uvw,ghi789rst
                 ↑TaskJournal  ↑アプリB    ↑アプリC
既存のキー（abc123xyz）を先頭にそのまま残せば、今の TaskJournal は何も変えなくてOKです。

Worker コードの変更箇所（1か所だけ）

変更前（今のコード）：

// 1本のキーと照合
if (!env.GEMMA_API_KEY || token !== env.GEMMA_API_KEY) {
  return json({ error: 'Unauthorized' }, 401, cors);
}

変更後：

// カンマ区切りで複数キーを受け付ける
const validKeys = (env.GEMMA_API_KEYS || env.GEMMA_API_KEY || '')
  .split(',').map(k => k.trim()).filter(Boolean);
if (validKeys.length === 0 || !validKeys.includes(token)) {
  return json({ error: 'Unauthorized' }, 401, cors);
}
古い GEMMA_API_KEY 変数もそのまま読み込むので、移行中でも安全
新アプリ用キーはコンマで足すだけ。Worker の再デプロイ不要

新しいアプリを追加するときの手順

1
新しいランダム文字列を用意（パスワード生成ツールで OK）
2
Cloudflare ダッシュボード → Worker → Settings → GEMMA_API_KEYS の値の末尾に ,新キー を追加して保存
3
新しいアプリの設定画面でその新キーを入力
4
以上！Worker のコードは変更不要

② パス制限（セキュリティ強化） 推奨

なぜ必要か

今の Worker は /v1/ 以外のパス（例：/admin、/etc/passwd）へのリクエストも転送してしまいます。

LM Studio 側にそういったエンドポイントはないので実害はありませんが、「使っていい道は /v1/ だけ」 と明示しておくのがベストプラクティスです。

Worker に追加するコード（3行）

// 上流URLを組み立てる部分の直前に追加
const inUrl = new URL(request.url);
if (!inUrl.pathname.startsWith('/v1/')) {
  return json({ error: 'Not Found' }, 404, cors);
}
const base = (env.UPSTREAM_BASE_URL || '').replace(/\/+$/, '');

③ ストリーミング対応 将来のため

ストリーミングとは

ChatGPT のように 文字が1つずつリアルタイムに出てくる 表示のこと。

技術的には「SSE（Server-Sent Events）」という仕組みを使います。AI側が stream: true で応答するとき、データが少しずつ届きます。

普通の返答 = レストランで料理が完成してから全部テーブルに運ぶ
ストリーミング = 前菜→スープ→メインと順番に運んでくれる

今の実装で既に対応できています

今の Worker コードは upstreamRes.body（ストリーム）をそのまま返しているため、特に変更なし でストリーミングは動きます。

ただし、タイムアウト設定に注意。Cloudflare Worker の無料プランは CPU時間30ms制限があるが、レスポンス待ちはカウントされないのでストリーミングも問題なし

④ 共通リファレンス（ドキュメント化） 推奨

なぜドキュメントが必要か

新しいアプリを作るたびに「エンドポイントURL何だっけ？」「モデル名は？」と迷うのを防ぎます。

シークレット（キー）は書かずに、接続に必要な公開情報だけをまとめます。

repo に追加するファイル: cloudflare/AI_GATEWAY.md

https://api.edaaiapps.com/v1/chat/completions

## モデル名
google/gemma-4-e4b

## 認証方式
Authorization: Bearer <あなたのアプリ用キー>

# ※キー自体はここに書かない。Cloudflare Worker の
#   GEMMA_API_KEYS (Secret) にカンマ区切りで管理。

## 新しいアプリを追加するとき

# 2. Cloudflare: GEMMA_API_KEYS の末尾に ,新キー を追加
# 3. アプリの設定画面に上のEndpoint/Model/キーを入力

⑤ LM Studio 常時稼働化 任意

今の問題

LM Studio は PC 起動のたびに手動で開いてモデルをロードする必要があります。複数アプリから使う場合、「なんか AI 動かない」→「あ、LM Studio 起動してなかった」が頻発します。

解決方法（LM Studio 0.3.5 以降 / 0.4系）

最近の LM Studio には 「ローカル LLM サービス（ヘッドレス）」 機能が組み込まれています。バッチファイルは不要で、設定をONにするだけで PC 起動時にGUIなしでサーバが自動稼働します。

1
LM Studio 起動 → Ctrl + , で設定を開き、左メニューの Developer を選択（Developer mode は ON に）
2

「ローカル LLM サービスを有効にする」（Enable Local LLM Service）を ON

→ LM Studio アプリを開いていなくてもサーバが動く＝常時稼働の本命

3

「JIT models auto-evict」（オンデマンドのモデル自動ロード）も ON にしておく

→ リクエストが来た瞬間に自動でモデルをロード。手動ロード不要に

→ 「最大アイドルTTL」は未使用時にモデルを解放する分数。すぐ応答させたいなら長め（例 1440分）に

4
一度 Developer タブでサーバを Start してON状態にしておく（次回以降は自動起動）
cloudflared(Tunnel) も常時稼働が前提。Windowsサービス化で確実に：管理者PowerShellで cloudflared service install。確認は Get-Service cloudflared が Running ならOK
確認：LM Studio を完全終了した状態で curl http://localhost:1234/v1/models がモデル一覧を返せば常時稼働成功
設定項目名・配置はバージョンで多少異なります（0.3.5で初導入、0.4系で名称変更あり）。見当たらなければ「Developer」タブと「App Settings」内を確認してください。

最終版 Worker コード

①②の変更を反映した完成版です。今の worker-openai-proxy.js を丸ごとこれに差し替えます。

/**
 * Cloudflare Worker - OpenAI互換プロキシ（複数キー対応版）
 *
 * 環境変数:
 *   GEMMA_API_KEYS   (Secret) カンマ区切りで複数キー可
 *                    例: key1,key2,key3
 *   GEMMA_API_KEY    (Secret) 旧変数。GEMMA_API_KEYS がなければこちらを使用（後方互換）
 *   CF_ACCESS_CLIENT_ID     (Secret)
 *   CF_ACCESS_CLIENT_SECRET (Secret)
 *   UPSTREAM_BASE_URL       (Text)  例: https://lmstudio.edaaiapps.com
 *   ALLOWED_ORIGINS         (Text)  例: https://idna7711-design.github.io
 */

export default {
  async fetch(request, env) {
    const origin = request.headers.get('Origin') || '';
    const cors = corsHeaders(origin, env);

    // 1. CORSプリフライト（認証より前に応答）
    if (request.method === 'OPTIONS') {
      return new Response(null, { status: 204, headers: cors });
    }

    // 2. /v1/ 以外のパスは拒否
    const inUrl = new URL(request.url);
    if (!inUrl.pathname.startsWith('/v1/')) {
      return json({ error: { message: 'Not Found' } }, 404, cors);
    }

    // 3. Bearer認証（複数キー対応）
    const auth = request.headers.get('Authorization') || '';
    const token = auth.startsWith('Bearer ') ? auth.slice(7).trim() : '';
    const validKeys = (env.GEMMA_API_KEYS || env.GEMMA_API_KEY || '')
      .split(',').map(k => k.trim()).filter(Boolean);
    if (validKeys.length === 0 || !validKeys.includes(token)) {
      return json({ error: { message: 'Unauthorized', type: 'invalid_api_key' } }, 401, cors);
    }

    // 4. 上流URLを組み立て
    const base = (env.UPSTREAM_BASE_URL || '').replace(/\/+$/, '');
    if (!base) {
      return json({ error: { message: 'UPSTREAM_BASE_URL not configured' } }, 500, cors);
    }
    const upstreamUrl = base + inUrl.pathname + inUrl.search;

    // 5. 上流ヘッダー設定
    const headers = new Headers();
    headers.set('Content-Type', request.headers.get('Content-Type') || 'application/json');
    headers.set('CF-Access-Client-Id', env.CF_ACCESS_CLIENT_ID || '');
    headers.set('CF-Access-Client-Secret', env.CF_ACCESS_CLIENT_SECRET || '');

    const init = {
      method: request.method,
      headers,
      body: (request.method === 'GET' || request.method === 'HEAD') ? undefined : request.body,
    };

    // 6. 転送してCORSヘッダーを付与して返す
    let upstreamRes;
    try {
      upstreamRes = await fetch(upstreamUrl, init);
    } catch (e) {
      return json({ error: { message: 'Upstream fetch failed: ' + e.message } }, 502, cors);
    }

    const outHeaders = new Headers(upstreamRes.headers);
    for (const [k, v] of Object.entries(cors)) outHeaders.set(k, v);

    return new Response(upstreamRes.body, {
      status: upstreamRes.status,
      statusText: upstreamRes.statusText,
      headers: outHeaders,
    });
  },
};

function corsHeaders(origin, env) {
  const allow = (env.ALLOWED_ORIGINS || '').split(',').map(s => s.trim()).filter(Boolean);
  let allowOrigin = '*';
  if (allow.length > 0) {
    allowOrigin = allow.includes(origin) ? origin : allow[0];
  }
  return {
    'Access-Control-Allow-Origin': allowOrigin,
    'Access-Control-Allow-Methods': 'GET, POST, OPTIONS',
    'Access-Control-Allow-Headers': 'Authorization, Content-Type',
    'Access-Control-Max-Age': '86400',
    'Vary': 'Origin',
  };
}

function json(obj, status, cors) {
  return new Response(JSON.stringify(obj), {
    status,
    headers: { 'Content-Type': 'application/json', ...cors },
  });
}

トラブルシューティング

「String contains non ISO-8859-1 code point」エラー

AI分類などで Failed to read the 'headers' property ... non ISO-8859-1 code point が出る場合、設定画面に入れた APIキーに半角でない文字（全角英数・スマートクォート・ダッシュ）が混入 しています。HTTPヘッダーは Latin-1 の文字しか使えないため、リクエストを作る前に弾かれます。

原因の特定（F12 → Console）：

// 256以上のコードポイント＝混入した文字を表示
[...settings.aiApiKey].filter(c => c.charCodeAt(0) > 255)

対処：設定画面でAPIキーを半角で入力し直す（パスワードマネージャ等プレーンな場所から貼る）。チャットやWord等の装飾付きテキストからのコピーは避ける（ハイフン - が – に化ける等）。

アプリ側にも aiAuthHeaders() でキーのtrim＋非ASCII検知を実装済み。混入時は分かりやすい警告が出る
